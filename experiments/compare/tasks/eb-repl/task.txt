Add a Workflow Lisp REPL to the orchestrator CLI.

What it is for. After an evaluated run (target 2.35 or 2.36), an author wants to inspect the values the program bound: in workflows/examples/plan_review_execute.orc these are `task`, `draft`, `feedback`, `revised` and the final value. Today `orchestrator report --format md` prints every committed effect result, but there is no way to evaluate an expression such as `feedback.findings` or `(list/length revised.steps)` against those bindings, and no way to load a module, run its entry and then inspect, from one interactive session.

Required behaviour of the first release.
1. A public CLI entry `orchestrator repl` (also `python -m orchestrator repl`) that starts an interactive read-eval-print loop.
2. Loading a module: the REPL is started with, or accepts a form that loads, an .orc source path with the same frontend flags `run` and `compile` take (`--source-root`, `--provider-externs-file`, `--prompt-externs-file`, `--command-boundaries-file`, `--imported-workflow-bundles-file`, `--entry-workflow`). Loading builds the checked closed program through the same build entry `compile` uses and reports compile diagnostics the same way.
3. Running: a form that runs the loaded entry with typed inputs goes through the same public run path `orchestrator run` uses (workspace lock, run authority, memo, providers), so the run is an ordinary run under .orchestrate/runs/<run_id> that `resume`, `report` and the dashboard understand. When the run halts, the REPL attaches to it.
4. Attaching: a form that attaches to an existing run id, read-only. Attaching replays the program against the memo without launching anything, exactly as the readers do (orchestrator/workflow/evaluated/views.py), and captures the lexical environment: at `halt` for a completed run, and at the first effect with no committed result for an interrupted or failed run, so that the bindings committed before the stop are inspectable. Attaching must not take the run writer lock and must not append to the memo.
5. Evaluating: after attaching, the user types pure Workflow Lisp expressions over the captured bindings (`feedback.findings`, `draft`, `(list/length revised.steps)`, `(= feedback.blocking (list))`). Each expression is read by the ordinary reader, typechecked by the ordinary typechecker against the module's types plus the captured bindings' types, lowered to a closed value through the ordinary closed-program builder, and evaluated with the ordinary evaluator in the captured environment. There is no second expression evaluator, no Python eval, and no reimplementation of operators. The REPL prints the value as canonical JSON and its type.
6. Refusals: an expression that performs or reaches an effect (provider-result, command-result, a call of an effectful procedure, run-ref, request-input, loops that contain effects) is refused with a named diagnostic code and no record is written anywhere. A free name that is not a captured binding or module definition is refused with the ordinary diagnostic. Attaching to a run whose program digest differs from the loaded module is refused with the existing `resume_program_changed` semantics or a named code of the same family.
7. Observability: `help`, listing the captured bindings with their types, and quitting. Nothing the REPL does changes the run's state, memo, view or files.

Facts established by a probe in this checkout, which the plan may rely on. Subclassing orchestrator.workflow.evaluated.machine._Machine and overriding _halt, while replaying a completed run with the same read-only effect handler views._replay uses (committed results from MemoSnapshot.active_commits, _MissingCommit otherwise), captured a LexicalEnvironment whose frames hold, innermost first, `%1`, `revised`, `feedback`, `draft`, `task` for the completed run of plan_review_execute.orc; `env.lookup("feedback")` returned an EvaluatedValue with a record descriptor, json_value() holding the findings, and dependencies naming the draft and feedback identities. orchestrator/workflow_lisp/typecheck_dispatch.py exposes typecheck_expression(expr, type_env=..., value_env=..., ...), and orchestrator/workflow_lisp/closed/build.py builds closed value nodes from typed expressions. orchestrator/workflow/evaluated/values.py exposes evaluate_closed_value(node, environment). orchestrator/cli/commands/evaluated.py exposes run_evaluated_workflow and resume_evaluated_workflow, and orchestrator/workflow/evaluated/authority.py exposes load_run_header and load_run_authority.

Constraints. The memo format, the closed-program schema, the run header and evaluator semantics do not change. The REPL holds no run writer lock while idle. No new third-party dependency; the standard library's readline is enough. New modules stay under 500 lines; split by responsibility. Tests are behavioural and go through public entries: at least one test runs a scripted-provider evaluated run of a small fixture module, attaches, evaluates a field access and a list operator, and checks the printed JSON; one test attaches to an interrupted run and finds only the committed bindings; one test shows an effectful expression is refused with its code and that the memo is byte-identical afterwards; no test asserts prompt text. Documentation: a design document from docs/templates/design_template.md under docs/design/, a row in docs/capability_status_matrix.md, routing in docs/index.md, a short section in docs/lisp_workflow_drafting_guide.md, and the CLI synopsis in specs/cli.md. Out of scope for this release: performing effects from the REPL, editing or hot-reloading a running program, a language server integration, flat-route (target 2.34 and earlier) runs, and any change to how runs are launched outside the REPL.

Public interface of the first release. Acceptance checks drive the REPL through exactly this surface, as a subprocess with forms on standard input, so implement it as written.

1. Command line: `orchestrator repl [SOURCE] [--source-root DIR] [--provider-externs-file FILE] [--prompt-externs-file FILE] [--command-boundaries-file FILE] [--imported-workflow-bundles-file FILE] [--entry-workflow NAME] [--run-id RUN_ID] [--state-dir DIR]`, also reachable as `python -m orchestrator repl`. Forms are read one per line from standard input, with or without a terminal; the process exits 0 after `:quit` or at end of input.
2. `--run-id RUN_ID` attaches to the run directory `<state dir>/RUN_ID`; the state directory is `--state-dir`, or `.orchestrate/runs` under the current directory. With SOURCE given, a loaded program whose digest differs from the run's is refused with `[resume_program_changed]` on standard error and exit status 2. Without SOURCE, the program is rebuilt from the run's recorded resume request (the `resume_request` field of the run's `run.json`), as `orchestrator resume` does, without creating `.orchestrate/build`; a run with no recorded resume request is refused with `[resume_request_missing]` and exit status 2, and nothing on disk changes.
3. After attaching, the REPL prints a line `position: P`. P is `halt` for a completed run; the effect identity recorded in the memo's `started` row for the first effect that has no committed result, for an interrupted run; or `failed:CODE` when the run failed in a pure expression, for example `failed:pure_expr_division_by_zero`. The captured environment is the lexical environment at that point; when that point is inside a called procedure, it is the callee's environment.
4. Commands:
   - `:bindings` prints one line per visible captured binding, `NAME : TYPE` (for example `draft : Plan`), the innermost binding of each name only.
   - `:result` prints the run's final value as a typed value (item 5); a run without one is reported as `[repl_no_result]` on standard error.
   - `:load SOURCE [the frontend flags of item 1]` loads a module.
   - `:run [--state-dir DIR] --input NAME=VALUE ...` runs the loaded entry through the public run path, in the session's state directory (item 2) or the command's `--state-dir`, prints `run_id: ID` and `exit_code: N` on their own lines, and attaches to that run.
   - `:help` and `:quit`.
5. Any other line is a pure expression. On success the REPL prints its value as one line of canonical JSON, then a line consisting of `: ` followed by its type, for example `: List[String]`. An expression that performs or reaches an effect is refused with `[repl_effect_refused]`; a free name that is neither a captured binding nor a module definition is refused with the ordinary `[name_unknown]`. Diagnostics go to standard error with their code in square brackets, and the session continues after a refusal.
