Harden checksum-compatible resume: before a resumed run executes anything, validate every persisted identity in the run state (step results, current step, loop progress, call frames and their lineage) against the current workflow projection, fail closed with one stable diagnostic, and never let that failure be routed, wrapped or downgraded.

What it is for. A run whose workflow source still has the same root checksum can nonetheless carry persisted identities the current program no longer owns: a stale or renamed step id, a loop iteration that cannot exist, a call frame whose caller or import alias changed, two resumable frames for one call. Today resume may select the wrong row, the wrong frame or the wrong callee by name, suffix or mapping order, and then mutate state or run effects. After this change resume audits each scope it will execute against the current projection and stops before any mutation or effect when the audit fails.

Required behaviour.

1. Scope audit and its ordering.
   - After schema and root-checksum acceptance, every ordinary root resume audits the persisted root scope against the current entry workflow's projection. The `orchestrator resume` command does this before observability overrides, executor session or process metadata, executor construction and the execution prologue; on failure it exits 1, prints the reason to standard error, and persists only the failure envelope of item 6.
   - A `WorkflowExecutor` that resumes as the structural root (not a child call-frame executor) rechecks the authoritative checksum (computing the current one through `StateManager.calculate_checksum`) and then audits the root scope, immediately before its prologue. A child call-frame executor does not repeat the root guard.
   - A reached call (a call step executing during resume) revalidates its frame shape, caller boundary, persisted import alias and lineage, so a checksum-compatible race cannot bypass them. It resolves its persisted caller identity against the current parent projection, with one call of `WorkflowStateProjection.resolve_call_boundary(slot_index, call_step_id)` (positional arguments) per reached call identity: exactly one current call boundary must own it, and that boundary's current import alias selects the callee bundle (the persisted alias is checked, it never redirects selection). Callee validation happens after the ordinary parent call visit/start publication and after the reached call's authored-input, managed/runtime-input, write-root, checksum and applicable resume-bound-input validation, but before the selected callee's frame or state is created or changed and before any callee effect. Nested scopes apply the same rule recursively.
   - The auditor reads nothing but the bundle and state it is given: it loads no workflow or bundle, computes no checksum and reads no file. It never mutates the state it audits.
   - Code that runs the audit (the call executor, the workflow executor and the resume command) calls it through a module-level name `audit_scope` in `orchestrator.workflow.calls`, `orchestrator.workflow.executor` and `orchestrator.cli.commands.resume`; acceptance checks substitute that name in each module to observe ordering.

2. Explicit identities and omission compatibility.
   - Every present explicit durable step identity (`steps.<name>.step_id`, `current_step.step_id`, `call_frames.<id>.call_step_id`) must resolve to exactly one candidate in its owning current scope. Stale, presentation-mismatched, out-of-scope, unclaimed, missing-required or ambiguous identities fail closed before effects. Qualified loop and call identities resolve only through projection-owned candidates: resume never splits, normalizes, prefix-matches, reconstructs, remaps or backfills ids, and never selects by workflow, module or procedure name, basename, path suffix or persisted alias.
   - An absent `step_id` stays compatible for every schema-valid `steps.*` row that the existing presentation/name/order fallback supports, whatever its status (completed, skipped, failed, running loop frame or result); resume leaves the field absent. A present `step_id` is always audited. `current_step.step_id`, `call_frames.*.call_step_id`, call-frame current position and loop progress selectors remain mandatory.

3. Loop projection integrity.
   - `for_each` bookkeeping: indices are unique non-boolean non-negative integers within `items`; the optional `current_index` is in range and not already completed.
   - `repeat_until` admits exactly four consistent progress forms: active; terminal condition success; terminal successful exhaustion with completed `on_exhausted` outputs; terminal failed exhaustion without them. Active progress has a non-negative `current_iteration` not in `completed_iterations` and consistent condition/result fields. Every terminal form has `current_iteration: null`, keeps the completed-iteration history, and identifies the terminal completed/evaluated iteration. Success has `last_condition_result: true` and is not exhausted. Successful exhaustion covers the declared maximum range, has `last_condition_result: false`, `exhausted: true` and a completed loop step. Failed exhaustion covers the declared maximum range, has `last_condition_result: false`, `exhausted` absent or false, and a failed loop step whose `error.type` is `repeat_until_iterations_exhausted`.
   - Valid bookkeeping does not excuse a stale or out-of-scope loop-local step id or loop-contained call-boundary id; exact candidate resolution still applies.

4. Call frames and Workflow Lisp retry lineage.
   - Every call frame validates its caller identity, import alias, boundary ownership and status. Completed frames are unlimited historical records and never resumable. A boundary whose callee is not Workflow Lisp has at most one non-completed frame; more is ambiguous.
   - A Workflow Lisp boundary is recognised only by the typed loaded-bundle capability `provenance.frontend_kind == "workflow_lisp"` (never by a `.orc` suffix or a name). Its non-completed frames form one retry lineage: a base frame id `B` (ordinal 0) and retries `B::retry::<n>` (n = 1, 2, ...), with zero or one running member and any number of failed predecessors. Mixed bases, more than one running member, a duplicate ordinal, a missing ordinal, a malformed or nested retry marker, an unknown status, a caller or alias that differs from the boundary's fail closed, never selecting by mapping order. The next fresh retry id is the lowest unused positive ordinal over all members (completed ones included), and allocation is deterministic.
   - With a running member: its checksum and resume-bound-input validation run first and win on failure; then every failed predecessor is checksum-validated and recursively audited in ordinal order; then the running member's own scope is audited and resumed. Without a running member: every failed predecessor is checksum-validated and recursively audited before the fresh retry frame is allocated. Failed predecessor state is never exempt.
   - A completed call frame whose id collides with the frame a resumed call would occupy is rejected before any lineage grouping, whatever its persisted `call_step_id` (matching, stale or missing), with the existing invalid-resume-state contract violation whose context is exactly `{"step", "call", "call_frame_id", "reason": "call_resume_state_invalid", "detail": "completed_call_frame_id_collision"}`; no child state manager or executor is created and the frames are unchanged.

5. Classic-YAML import aliases, before bundle construction (`WorkflowLoader.load` raises `WorkflowValidationError` and `orchestrator.loader.build_loaded_workflow_bundle` is never reached).
   - An import alias that occurs more than once among the effective `imports` entries — duplicate keys, a YAML `<<` merge inside `imports`, repeated top-level `imports` sections, or top-level `<<` merge sources that each carry `imports` — is reported once as `imports.<alias>: duplicate import alias`, naming the position of each occurrence as `line L, column C` (1-based, the alias key). A repeated alias is not also reported as a duplicate section.
   - Repeated top-level `imports` sections (direct, or one merged and one explicit) whose aliases are all distinct are reported once as `imports: duplicate top-level mapping`, naming the position of each `imports` key the same way, and not as a duplicate alias.
   - A single merged `imports` section and unique aliases still load.

6. Failure and mutation envelopes.
   - The initial CLI root-checksum precheck keeps its existing behaviour (exit 1, nothing written) before any session or executor exists.
   - A structurally root executor whose checksum recheck fails persists `error` = `{"type": "workflow_checksum_mismatch", "message": "Workflow has been modified since the run started", "context": {"workflow_file", "persisted_checksum", "current_checksum", "reason"}}`, where the first three are strings or JSON null and `reason` is exactly one of `workflow_modified`, `missing_recorded_checksum`, `missing_workflow_path`, `workflow_unavailable`. It changes only the root `status` (to `failed`), `error` and `updated_at`, and stops before the projection audit and the prologue. Already-open session/process metadata may remain; a failing session close cannot replace the diagnostic.
   - A root projection failure (CLI or executor) changes only the root `status`, `error` and `updated_at`. A checksum-compatible identity change caught by the executor's second root audit after the CLI audit passed uses the same three-field delta, keeps already-open session/process metadata, stops before the prologue and closes the executor session as failed without replacing the diagnostic. An unchanged `current_step` left by such an envelope (error type `resume_projection_integrity_error` or `workflow_checksum_mismatch`) is forensic: the run is reported failed with its error, and the status snapshot (`build_status_snapshot`) shows that step as `pending` (status and summary `pending`, `current_visit_count` null, counted under `pending`, not `running`), and `render_status_markdown` does not call it `in progress`; heartbeat and stalled-run interpretation likewise do not treat it as live.
   - A reached-callee failure before the callee is constructed becomes the caller's failed call-step result and the scope/run error; the selected callee frame and state stay untouched; existing ancestor frames persist ordinary failed step/current/visit/frame snapshots and promote the exact same diagnostic, unchanged, to the root. It is never wrapped in `call_failed`.
   - `resume_projection_integrity_error` is a sticky, non-routable terminal failure: authored `success`, `failure` and `always` routes, `on_error=continue`, and `for_each`/`repeat_until` continuation cannot consume it (the run stops; no next iteration). Configured finalization may still run, but a finalization failure is supplemental: it is recorded under `finalization` as `status: failed` and `failure` = `{"step": <cleanup step name>, "step_id": <its step id>, "error": <the cleanup's projection error, or null for an ordinary failure>}`, and it never wraps, replaces, clears or downgrades the run's projection diagnostic. When the projection error arises only inside finalization, it becomes the run error and `finalization.failure.error`. Epilogue and session close preserve it.

7. Diagnostics and privacy.
   - Every audit failure is `{"type": "resume_projection_integrity_error", "message": "Resume projection integrity audit failed: <reason>", "context": {...}}` with context keys, all always present: `diagnostic_schema` = `"resume_projection_integrity_error.v1"`; `reason` (one of the twelve below); `scope_path` (identity-only list: `{"kind": "root", "workflow_file": <file>}` then one `{"kind": "call_frame", "frame_id": <id>}` per call frame entered); `field` (the dotted path of the offending persisted field, or null); `offending_value` (the offending scalar, or null when absent or when the value is a container); `expected_owner` = `{"workflow_file", "workflow_checksum", "projection_scope"}` (the audited bundle's workflow file, the audited state's `workflow_checksum`, and `"root"` or `"call_frame"`); `candidate_count` (integer, or null when no candidate search applies); `call_boundary_step_id` (the audited frame's call step id, or null).
   - Reasons, with the field/offending value/candidate count they carry:
     - `unknown_explicit_step_id`: a step row's `step_id` matches no current candidate (`steps.<name>.step_id`, the id, 0).
     - `presentation_slot_mismatch`: the id exists but belongs to another presentation slot (`steps.<name>.step_id` or `current_step.step_id`, the id, 1).
     - `out_of_scope_step_id`: `current_step.step_id` or a frame's `call_step_id` is not a step of the scope (that field, the id, 0).
     - `unclaimed_explicit_step_row`: a row with an explicit `step_id` whose presentation name the current scope does not own (`steps.<name>.step_id`, the id, 0).
     - `missing_required_identity`: a mandatory identity is absent (for example `current_step.step_id`; null, null).
     - `missing_call_boundary`: a frame's `call_step_id` is a valid local step but not a current call boundary (`call_frames.<id>.call_step_id`, the id, 0, and `call_boundary_step_id` = that id).
     - `ambiguous_call_boundary`: more than one current boundary owns the caller id (`call_frames.<id>.call_step_id`, the id, the count).
     - `ambiguous_resumable_call_frame`: more than one resumable frame for one boundary (`call_frames`, the number of resumable frames, that number).
     - `persisted_import_alias_mismatch`: a frame's `import_alias` differs from the boundary's current alias (`call_frames.<id>.import_alias`, the persisted alias, 1).
     - `missing_imported_bundle`: the boundary's alias selects no loaded import (`imports.<alias>`, the alias, 1).
     - `unsupported_shape`: a container or value has the wrong shape: `steps` not a mapping (field `steps`), `call_frames` not a mapping (field `call_frames`), a frame that is not a mapping (field `call_frames.<frame id>`), a malformed step row or identity value; the offending value is null for containers and never shows their contents.
     - `invalid_loop_progress`: loop bookkeeping violates item 3 (for example `repeat_until.<loop>.completed_iterations`).
   - Diagnostics never expose bound inputs, context values, artifacts, prompts, provider output, secrets, whole frame state, whole projections, or the contents of a malformed list or mapping used as an identity.
   - The auditor reads no procedure-migration, identity-retirement or other migration evidence, keeps no receipts and no persisted audit cache. State schema stays "2.1"; pre-v2.0 state and pre-2.1 reusable-call state remain rejected.

8. Typed Workflow Lisp provenance. Every bundle produced by the Workflow Lisp compiler (`compile_stage3_entrypoint`'s validated bundles, including imported Workflow Lisp bundles reached through `imports`, and every lowered bundle) carries `provenance.frontend_kind == "workflow_lisp"`. A classic-YAML bundle passed in through `imported_workflow_bundles` keeps its own provenance (`frontend_kind` stays None) and is linked as the same object. `build_frontend_bundle` keeps whatever `frontend_kind` the compiler set on the selected bundle instead of overwriting it.

Public interface checked by acceptance tests.

- `orchestrator.workflow.resume_projection_integrity` (new module):
  - `ResumeScopePath`: frozen dataclass with fields `root_workflow_file: str` and `call_frame_ids: tuple[str, ...] = ()` (an input list is snapshotted to a tuple); `ResumeScopePath.root(workflow_file)`; `.child(frame_id)` returns the path one frame deeper; `.projection_scope` is `"root"` or `"call_frame"`; `.as_context()` returns the `scope_path` list of item 7.
  - `audit_scope(bundle, state, scope_path) -> None` audits one scope (item 1) and raises `ResumeProjectionIntegrityError`, a `ValueError` whose `.error` is the diagnostic dict of item 7.
  - `index_retry_lineage(boundary_step_id, frame_items, *, frontend_kind) -> CallFrameRetryLineage`, where `frame_items` is an iterable of `(frame_id, frame)` pairs and a frame has `status`, `call_step_id` and `import_alias`. `CallFrameRetryLineage` has `base_frame_id`, `completed_members` (all completed frames, any number), `failed_predecessors` (in ordinal order) and `running_member` (or None); members have `frame_id` and, for lineage members (`RetryFrameMember`), `ordinal`. For a non-Workflow-Lisp boundary (`frontend_kind` other than "workflow_lisp") the single non-completed frame, if any, is `running_member`. Invalid input raises `CallFrameRetryLineageError`, a `ValueError` with `.reason`: `ambiguous_resumable_call_frame` (several running members, mixed bases, a duplicate ordinal, or several non-completed frames of a non-Workflow-Lisp boundary), `unsupported_shape` (a missing or malformed ordinal, a nested retry marker, an unknown status), `missing_call_boundary` (a frame whose `call_step_id` is not the boundary), `persisted_import_alias_mismatch` (frames with different aliases).
  - `next_unused_retry_frame_id(lineage) -> str` returns `<base>::retry::<lowest unused positive ordinal>`, idempotently.
- `orchestrator.workflow.state_projection`:
  - `ResumeProjectionValidationError(ValueError)` with `.reason` and `.message`, and `str()` equal to the message.
  - `WorkflowStateProjection.enumerate_resume_slots(state) -> ResumeProjectionSlotIndex`, with `candidates_by_step_id` (step id -> tuple of candidate slots), `call_boundaries_by_step_id`, and `unclaimed_explicit_rows` (tuple of `(row name, step_id)` pairs for explicit rows no candidate claims; the step id as persisted, snapshotted, even when unhashable). It does not mutate or backfill the state and raises `ResumeProjectionValidationError` for invalid loop bookkeeping with exactly these reasons and messages (for a `for_each` named `ProcessItems` and a `repeat_until` named `ReviewLoop`):
    - unsupported_shape: `for_each must be a mapping`, `for_each.ProcessItems must be a mapping`, `for_each.ProcessItems.items must be a list`, `for_each.ProcessItems.current_index must be null or a non-boolean integer`, `repeat_until must be a mapping`, `repeat_until.ReviewLoop must be a mapping`, `repeat_until.ReviewLoop.current_iteration must be null or a non-boolean integer`, `repeat_until.ReviewLoop.exhausted must be boolean when present`;
    - invalid_loop_progress: `for_each.ProcessItems.completed_indices must not contain duplicate indices`, `for_each.ProcessItems.completed_indices contains an out-of-range index`, `for_each.ProcessItems.current_index is already completed`, `repeat_until.ReviewLoop.completed_iterations must not contain duplicate indices`, `repeat_until.ReviewLoop.current_iteration is out of range`, `repeat_until.ReviewLoop.completed_iterations is not valid prior history`, `repeat_until.ReviewLoop.condition result conflicts with evaluation state`, `repeat_until.ReviewLoop.terminal progress requires completed evaluated history`, `repeat_until.ReviewLoop.successful exhaustion requires a completed frame`, `repeat_until.ReviewLoop.failed exhaustion requires the terminal exhaustion error`.
  - `WorkflowStateProjection.resolve_resume_step_id(slot_index, step_id, presentation_key=None) -> ResumeIdentityResolution` with `.slot` (the unique matching candidate, or None; a slot has `node_id`, `region` whose `.value` is for example "finalization", and `iteration_index` for loop-local ids), `.candidate_count` (candidates for the id) and `.exact_identity_candidate_count`; an unhashable or malformed id resolves to no candidate (count 0) instead of raising.
  - `WorkflowStateProjection.resolve_call_boundary(slot_index, call_step_id) -> ResumeCallBoundaryResolution` with `.boundary` (the unique `CallBoundaryProjection`, or None) and `.candidate_count`.
  - `CallBoundaryProjection` gains the field `import_alias` (the boundary's current authored alias), constructible by keyword alongside its existing fields.
- `orchestrator.state.StateManager`:
  - `record_workflow_checksum_mismatch(*, workflow_file, persisted_checksum, current_checksum, reason)` persists the checksum envelope of item 6 atomically, changing only `status`, `error` and `updated_at` (unknown root fields and the run tree are preserved; it does not call `fail_run`).
  - `record_resume_projection_integrity_failure(error)` persists the given diagnostic the same way, changing only `status`, `error` and `updated_at`.
- Existing entries the checks also drive, unchanged in signature: `orchestrator.cli.commands.resume.resume_workflow`, `WorkflowExecutor.execute(resume=...)`, `CallExecutor.execute_call`, `CallExecutor._is_workflow_lisp_target(bundle)` (now true exactly when `provenance.frontend_kind == "workflow_lisp"`), `WorkflowExecutor._handle_control_flow` (returns the existing `"_stop"` for a sticky projection result), `WorkflowStateProjection.call_boundary_runtime_step_id`, and the observability `build_status_snapshot` / `render_status_markdown`.
- Codes and literals: `resume_projection_integrity_error`, `resume_projection_integrity_error.v1`, the twelve reasons above, `workflow_checksum_mismatch`, `Workflow has been modified since the run started`, `workflow_modified`, `missing_recorded_checksum`, `missing_workflow_path`, `workflow_unavailable`, `repeat_until_iterations_exhausted`, `call_resume_state_invalid`, `completed_call_frame_id_collision`, `call_resume_checksum_mismatch` (an existing reached-call checksum failure that must still take precedence where item 4 says so), `imports.<alias>: duplicate import alias`, `imports: duplicate top-level mapping`, `line L, column C`, `::retry::<n>`.
- The auditor module must not import `orchestrator.workflow_lisp.migration_parity` or `orchestrator.workflow_lisp.procedure_identity_retirement` nor use `load_parity_targets`, `load_retirement_evidence`, `load_retirement_record` or `validate_retirement_record`, and no identifier, attribute, key or string in it may contain `receipt`, or `cache` together with `audit`, with `resume projection` or with `projection integrity`.

Constraints. No change to the state schema version, the memo or run layout. No receipts, persisted audit caches, migrations or unrelated resume refactors. No new third-party dependency. New modules stay under 500 lines where practical; split by responsibility. Tests are behavioural and go through public entries; no test asserts prompt text. Documentation: the contract in `specs/state.md` (a section on checksum-compatible resume projection integrity) and its acceptance entries in `specs/acceptance/index.md`.
