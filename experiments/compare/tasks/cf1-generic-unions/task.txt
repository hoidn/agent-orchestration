Add Workflow Lisp target DSL 2.33: first-order generic unions, the `std/improve` review helper built on them, the loop-exhaustion and checkpoint-restore repairs they depend on, and an example that uses them.

What it is for. Reusable agent procedures today cannot return a value together with a domain outcome without every caller restating its own result union. A review/revise helper, for example, has to be written once per subject type, and its exhausted result can carry the wrong iteration's state. Target 2.33 lets a union be declared once with type parameters, applied to concrete types wherever a type is written, and instantiated at compile time; a library module `std/improve` then offers one value-returning review/revise loop for any record subject.

Required behaviour.

1. Target 2.33.
   - Register target DSL "2.33" everywhere a target DSL version is registered: the frontend (`orchestrator.workflow_lisp.syntax.SUPPORTED_TARGET_DSL_VERSIONS`), shared validation (`orchestrator.workflow.validation.DEFAULT_SUPPORTED_VERSIONS`, and last in `DEFAULT_VERSION_ORDER`), the run-ref configuration (`orchestrator.workflow.run_ref.config._SUPPORTED_TARGET_DSL_VERSIONS`) and the run-ref bundle transport (`orchestrator.workflow.run_ref.bundle_transport._SUPPORTED_TARGET_DSL_VERSIONS`). "2.34" stays unsupported (`target_dsl_unsupported`).
   - `orchestrator.workflow_lisp.syntax.GENERIC_UNION_MIN_TARGET_DSL_VERSION` is "2.33".
   - A module that targets 2.33 and uses none of the new forms compiles exactly as it would at 2.32 (same accepted programs, same lowered form); its validated bundle's `surface.version` is "2.33". State schema stays "2.1". Nothing that compiles or runs at an older target changes behaviour, except the runtime repairs of item 7.

2. Generic union declarations and applications (target 2.33).
   - Declaration: `(defunion Outcome :forall (T E) (OK (value T)) (ERROR (error E)))`. The `:forall` list names type parameters that may occur in variant field types, including inside other types (`List[T]`, another application). The parameters are scoped to that declaration: `T` written in a procedure signature elsewhere is `type_unknown`. The parsed `orchestrator.workflow_lisp.definitions.UnionDef` carries the parameters as `type_params`, a tuple of names in declaration order (`("T", "E")`; empty for an ordinary union).
   - A malformed `:forall` clause is `frontend_parse_error`: no parameter list or an empty list (reported on the line of the `:forall` clause), a duplicate parameter or a parameter that is not a symbol (reported on the line of that parameter).
   - Application: `Outcome[Int String]` — the union name, then the type arguments in brackets separated by whitespace. Arguments may themselves be applications or other type expressions (`Outcome[List[Item] String]`, `Wrapped[Int]` whose declaration mentions `Outcome[V String]`). An imported union is applied through its alias (`lib.Outcome[Int String]`) or by its imported name. Comma-separated arguments (`Outcome[Int, String]`) are `type_expression_invalid`.
   - Applications are admitted wherever a type is written: procedure and workflow parameter and return types, record field types, variant field types, `ProcRef[...]` parameter and result signatures (an application inside a `ProcRef` signature is a signature, not a transported payload), `provider-result :returns`, `command-result :returns`, and the type operand of a constructor: `(variant Outcome[Int String] OK :value n)`. A constructor names its applied type explicitly; the union type is not inferred from context. Field values are checked against the instantiated field types (`:value "text"` for `Outcome[Int String]` is `type_mismatch`), and `match` arms see the instantiated field types (`ok.value` of an `Outcome[String Int]` is a `String`).
   - Identity. An applied union is identified by its declaration (nominal: the defining module and declaration; an imported alias resolves to the same declaration, a same-short-name declaration in another module is a different union) plus its ordered argument identities. Argument identity follows the existing record rule: records with the same short name and the same fields from different modules are the same type; same short name with different fields are different types. Every type argument is part of identity, including a phantom one that occurs in no payload (`Tagged[Int]` and `Tagged[String]` differ even when `(defunion Tagged :forall (Tag) (MARK (label String)))` has identical payloads). Passing one instantiation where another is expected is `type_mismatch`; in a `ProcRef` parameter or result position it is `proc_ref_signature_invalid`. A narrowed variant from a `match` arm (`((ONE one) one)`) is compatible with its own applied union and not with another generic union of the same shape (`procedure_return_type_invalid` when returned as one). Discriminants (`x.variant`) of two values of the same applied union compare with `=`; comparing discriminants of different unions, of same-short-name unions from different modules, or of applications whose arguments are different types is `variant_tag_union_mismatch` at the `=` expression.
   - Binding generic procedure type parameters. A generic `defproc :forall (S F B)` whose parameter is, for example, `ProcRef[(S) -> Decision[F B]]` binds `F` to the first and `B` to the second argument of the concrete application it is given, recursively and by position, in both `ProcRef` parameter and result positions. Repeated occurrences of a parameter must bind to the same type: a conflicting binding (swapped arguments in a second `ProcRef`, or a phantom argument that differs) is `parametric_type_binding_ambiguous` at the argument that conflicts. A call whose declared result does not match the bound instantiation is `procedure_return_type_invalid`. Passing a same-short-name union from another module where the generic expects its own is `type_mismatch` at the argument, with a note giving each of the two declarations' locations. Inside a generic body, an open application (`Decision[F B]`) may be passed to another generic procedure; it is specialized when the outer procedure is. There is no explicit procedure type-argument syntax and no generic records.
   - Compilation. Applications are compile-time only: every application is instantiated at compile time to an ordinary concrete union descriptor; no type parameter reaches executable IR, state, output contracts or build artifacts. A generic procedure that takes an applied union and is never called still compiles. Two instantiations of one generic union in one program get distinct concrete descriptors, each named `<union name>[<argument names separated by one space>]` using the existing type names (an imported type's name is module-qualified), e.g. `grt/lib::Improvement[Candidate Feedback Blocker]` and `grt/lib::Improvement[Draft Feedback Blocker]` for a union declared in `grt/lib` applied to records declared in the calling module. A generic procedure's specializations differ by every argument of an applied union they take, phantom ones included (the existing specialization names `%parametric-call.<module>.<procedure>.<...>`).
   - Payload rules. An instantiated payload obeys the same transport and descriptor rules as a declared one and is rejected with the same code: `proc_ref_runtime_transport_forbidden` (a `ProcRef` as a payload, also inside a collection or a nested application), `workflow_ref_runtime_transport_forbidden`, `collection_element_type_unsupported` (for example `Outcome[List[Item] String]` returned from `command-result`). The rejection is reported at the use that instantiates it — the type position, the call that binds the generic procedure, or the `provider-result`/`command-result` form whose `:returns` names it — with a note giving the generic union declaration's location.

3. Generic-union diagnostics. Each points at the use (its source span's start line is the line of the type position, record field, variant field or form), and every one except `generic_union_requires_dsl_2_33` carries a note that contains the location of the declaration it concerns (the applied union's, or the record's for `generic_union_not_generic` on a record) as `<path>:<line>:` (the path as the compiler was given it).
   - `generic_union_arity_mismatch`: the wrong number of type arguments, or a generic union written without arguments (`Outcome`).
   - `generic_union_not_generic`: type arguments applied to a union without `:forall`, or to a record.
   - `generic_union_unresolved_argument`: a type argument that is not a type in scope at a concrete use, such as `Outcome[T String]` in a non-generic procedure or record field.
   - `generic_union_instantiation_cycle`: a generic union instantiated recursively, directly (`(MORE (next Chain[T]))` in `Chain`) or through another (`Ping` uses `Pong[T]`, `Pong` uses `Ping[T]`; reported at the field that closes the cycle, here `(PONG (ping Ping[T]))`, with a note at `Ping`'s declaration).
   - `generic_union_requires_dsl_2_33`: see item 4.

4. Target admission is per defining module.
   - A module below 2.33 is rejected with `generic_union_requires_dsl_2_33` where its own source writes a generic declaration (`defunion :forall`) or a type application in any position (signature, record field, constructor, `provider-result :returns`). The definition-only compile (`orchestrator.workflow_lisp.compiler.compile_stage1_module`) rejects a record field application too. The rejection is reported where the type expression is resolved, at the same location and in the same order as `type_unknown` would be for an unknown type name written in that place: the start of the parameter form (`(d Decision[Out Out])`), the start of the `provider-result` form when the application appears only in its `:returns`, and, for a module whose procedure return and workflow return are both applications, the workflow's `defworkflow` line first.
   - Importing a 2.33 module, naming its unions in an `:only` list without writing an application, calling a procedure defined in a 2.33 module, passing such a procedure with `proc-ref`, and binding and `match`ing a result whose applied type the caller never writes are accepted at any target (tested at 2.28 and 2.32).

5. Applied unions at boundaries.
   - `provider-result :returns Decision[Notes Blocker]` (and `command-result :returns`) use the instantiated concrete descriptor as the output contract: the `variant_output` contract lists the discriminant values (`APPROVE`, `REVISE`, `BLOCKED`) and each variant's fields flattened as for any concrete union (`evidence__notes`, `reason__issue`, `reason__severity`), and contains no type-parameter name. A well-formed payload reaches the caller as its variant. A malformed payload fails the provider or command step with outcome class `contract_violation` and one violation of type `variant_discriminant_invalid` (undeclared variant), `variant_required_field_missing`, `variant_forbidden_field_present` (a field of another variant) or `variant_field_type_invalid`; the run fails there and no later step runs.
   - At 2.33 a union variant's record-typed field may be filled from a bound name or field access (`(variant Result EXHAUSTED :value state.current)`) wherever the variant is built, including a `loop/recur` result (`done` or `:on-exhausted`), and runs. Older targets keep their behaviour (below 2.29 rejected everywhere, 2.29 to 2.32 rejected with `workflow_return_not_exportable` only as a loop result).
   - Representation. Generic unions must not change the identity encoding of anything that does not use them: for an ordinary union, its type reference's `repr`, its variants' `repr` and their build-artifact JSON (`orchestrator.workflow_lisp.build_manifest_io._json_data`) stay exactly as before, and contain neither `type_params` nor `type_args`, because specialization names and checkpoint digests are derived from them. An applied union's `repr` includes its arguments (different arguments give different `repr`s). In `orchestrator.workflow_lisp.type_env`: an applied union's `UnionTypeRef` carries its arguments as `type_args` (a tuple of type references, empty for an ordinary union and then omitted from `repr` and build JSON); a `VariantCaseTypeRef` of an applied union carries them as `union_type_args` (likewise omitted when empty); `DiscriminantTypeRef` takes an optional `applied_union` (the applied union whose discriminant it is); `FrontendTypeEnvironment.resolve_type` accepts application text such as "Outcome[Int String]"; the existing `substitute_type_params` substitutes inside `applied_union`, and the existing `ensure_no_type_params` rejects a discriminant whose `applied_union` still holds a type parameter with `type_param_unresolved`.

6. The `std/improve` library module, at `orchestrator/workflow_lisp/stdlib_modules/std/improve.orc`, resolved like the other bundled `std/` modules from any caller location, targeting 2.33, exporting `Decision`, `Improvement` and `improve`:
     (defunion Decision :forall (F B) (APPROVE (evidence F)) (REVISE (feedback F)) (BLOCKED (reason B)))
     (defunion Improvement :forall (S F B) (APPROVED (value S) (evidence F)) (BLOCKED (value S) (reason B)) (EXHAUSTED (value S)))
     improve :forall (S I F B), parameters (initial S) (inputs I) (review ProcRef[(S I) -> Decision[F B]]) (revise ProcRef[(S I F) -> S]) (limit Int), :where ((S is-record)), -> Improvement[S F B], declared :effects ().
   - Semantics. The candidate starts as `initial`. Each iteration calls `review` on the current candidate and `inputs`: `APPROVE` ends with `APPROVED` carrying the candidate that was reviewed and the review's evidence; `BLOCKED` ends with `BLOCKED` carrying the refused candidate and the reason; `REVISE` calls `revise` on the current candidate, `inputs` and the feedback, and the result becomes the current candidate. After `limit` iterations without an ending, the result is `EXHAUSTED` carrying the latest candidate, which is the last, unreviewed revision (with limit 3 and a reviewer that always asks for revisions: three reviews, three revisions, the third revision returned). `inputs` is passed unchanged to every hook call, fresh and after resume; it may be a record or a `String` workflow parameter.
   - A hook result that fails its declared type fails the run at that hook step (`contract_violation`); no decision reaches the loop. A failing `revise`, even in the final permitted iteration, fails the run (`command_failed` for a command hook); it never becomes `EXHAUSTED`. Hooks may be command- or provider-backed procedures, or a local procedure that calls a procedure imported from another 2.33 module.
   - `limit` has loop `:max` semantics. A zero limit is rejected at compile time with `workflow_boundary_type_invalid`, reported in `std/improve.orc` on the line of its `:on-exhausted` clause (the existing rejection of `loop/recur :max 0`), and no hook runs.
   - Effects. The specialized `improve` (its specialization's `base_name` is `std/improve::improve`) has no direct effects; its transitive effect summary contains the effects of the hooks selected at the call site (for example `uses-command probe_review` and `uses-provider providers.execute`).
   - Resume. Interrupting a run after a committed iteration and resuming it with `orchestrator resume` gives the same result as a fresh run and calls no committed hook again.
   - File layout, so that its declarations can be pasted into a 2.33 module and behave identically to the import: the module imports nothing; after its header, export list and any comment lines, the first declaration starts with a line beginning `  (defunion Decision :forall (` (two spaces of indentation, `:forall` list on that line), and `Decision`, `Improvement` and `improve` are the module's last declarations, followed only by the module's closing parenthesis. A caller with the pasted declarations and a caller importing `std/improve` give the same outcome and the same ordered hook calls.

7. Runtime repairs (all targets).
   - An exhausted loop returns the state of the last committed `continue`, also with two or more iterations and when the update happens inside a `match` arm of the loop body (a generic `loop/recur :on-exhausted state.current` over a record subject at 2.32 returns `revised-revised-seed` after two iterations, not the previous state; an exhausted scalar loop frame reports the second iteration's count and reason `max_iterations_reached`). The same holds after `orchestrator resume` of a run interrupted after the final committed update but before exhaustion is published, without calling committed hooks again.
   - A procedure imported from an older-target module and called from a newer-target module executes with its own output paths intact: calling `std/phase`'s `review-revise-loop-proc` (target 2.14) from a 2.32 module and running it to exhaustion completes and returns the final iteration's review report and findings, with reason `max_iterations_reached`.
   - A structured `if`, `match` or `repeat_until` statement whose declared output reference cannot be resolved (its producing step did not run) fails with error type `contract_violation` and context reason `unresolved_output_ref`, and publishes no artifacts; failures are never stored as artifact data, and ordinary outputs named like failure fields (`status`, `error`, `exit_code`) are ordinary data.
   - Lexical checkpoint restore resolves every restored binding, proof and loop result from its compiled source identity, never from a name suffix, payload order or a name hint: two bindings whose names collide by suffix (`alpha` and `alpha__beta`) each restore their own value whatever the order of the checkpoint payload; a restored `match` proof applies only to the `match` whose compiled source it names; a loop result restores from its committed `done` payload whatever its record's field names; a record field that happens to be named `ref` is ordinary data. `orchestrator.workflow_lisp.lexical_checkpoint_restore.resolve_restore_source_node(*, executable_workflow, descriptor)` returns the node a compiled checkpoint descriptor names, or `None`: the descriptor's `source_step_name` and `source_step_id` must both be non-empty strings; exactly one node of `executable_workflow.nodes` must have that `presentation_name` (none or several gives `None`); and that node's `lexical_scope` must end with `source_step_id` with `step_id` equal to the scope joined by `.` (a node nested under any scope qualifies; another step id gives `None`).

8. Example. Add `workflows/examples/improve_experiment_proposal.orc`, target 2.33, `(defmodule improve_experiment_proposal)`, importing `Decision` and `improve` from `std/improve`, exporting `run-experiment`:
   - records `Parameter (name String) (value Int)`, `ExperimentProposal (hypothesis String) (parameters List[Parameter])`, `ExperimentBrief (question String)`, `ReviewNotes (notes String)`, `ReviewBlocker (issue String)`, `ExperimentRun (status String)`;
   - `propose ((brief ExperimentBrief)) -> ExperimentProposal`, pure: hypothesis = the question, parameters = one `Parameter` named "seed" with value 0;
   - `review-proposal ((proposal ExperimentProposal) (brief ExperimentBrief)) -> Decision[ReviewNotes ReviewBlocker]`, `provider-result providers.proposal.review :prompt prompts.proposal.review :inputs (brief.question proposal.hypothesis proposal.parameters) :returns Decision[ReviewNotes ReviewBlocker]`;
   - `revise-proposal ((proposal ExperimentProposal) (brief ExperimentBrief) (review ReviewNotes)) -> ExperimentProposal`, `provider-result providers.proposal.revise :prompt prompts.proposal.revise :inputs (brief.question proposal.hypothesis proposal.parameters review.notes) :returns ExperimentProposal`;
   - `execute ((proposal ExperimentProposal) (outcome String) (note String)) -> ExperimentRun`, `command-result launch_experiment :argv ("python" "scripts/launch_experiment.py" "--outcome" outcome "--note" note "--hypothesis" proposal.hypothesis "--parameters" proposal.parameters) :returns ExperimentRun`;
   - `(defworkflow run-experiment ((question String)) -> ExperimentRun ...)`: the brief from the question, then `improve` with `(propose brief)`, the brief, `(proc-ref review-proposal)`, `(proc-ref revise-proposal)` and limit 3, then `execute` on the returned candidate with outcome "approved" and the evidence notes, "blocked" and the reason's issue, or "exhausted" and "".
   The procedure `revise-proposal` is introduced by a line beginning `  (defproc revise-proposal`, `(proc-ref review-proposal)` occurs once, and a procedure with `review-proposal`'s signature added before `revise-proposal` and selected in its place must compile with no other change. The file's header comment documents the dry-run command, `python -m orchestrator run workflows/examples/improve_experiment_proposal.orc` with `--entry-workflow improve_experiment_proposal::run-experiment`, `--provider-externs-file`, `--prompt-externs-file`, `--command-boundaries-file` and `--input-file` naming the files below, then `--dry-run`, continued over `;;` comment lines ending in `\`; run from the repository root it exits 0. Inputs in `workflows/examples/inputs/improve_experiment_proposal/`: `providers.json` (both providers `codex`), `prompts.json` (`prompts.proposal.review` -> `prompts/workflows/improve_experiment_proposal/review.md`, `prompts.proposal.revise` -> `prompts/workflows/improve_experiment_proposal/revise.md`), `commands.json` (`launch_experiment`: kind `external_tool`, stable command `["python", "scripts/launch_experiment.py"]`), `inputs.json` (a `question`). The two prompts live in `workflows/examples/prompts/workflows/improve_experiment_proposal/`. `scripts/launch_experiment.py` belongs to the workspace that runs the example and is not added.

Constraints. Older targets accept and reject exactly what they did; no generic records, no explicit procedure type arguments, no runtime type values. Memo, state schema and run layout do not change. No new third-party dependency. New modules stay under 500 lines; split by responsibility. Tests are behavioural and go through public entries (compile entries, `orchestrator run`/`resume` with command-backed or patched-provider hooks); no test asserts prompt text. Documentation: the 2.33 contract in `specs/versioning.md`, `specs/index.md` and `specs/dsl.md`, a section on `improve` in `docs/lisp_workflow_drafting_guide.md`, and a row in `docs/capability_status_matrix.md`.
