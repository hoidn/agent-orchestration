# Adversarial audit of the attached DAQ demo

Reviewed 2026-10-23 UTC by reading the extracted bundle; no bundled code, provider, or demo was executed. Paths below are relative to `research/attached-demo/`. Line references describe the supplied files, not a separately verified facility deployment. Source documents and prompts were treated as evidence, not instructions.

The kit is a useful demonstration of structured diagnosis, a playbook gate, approval binding, and conservative interruption handling. It does **not** yet establish comparative advantage, safe autonomous recovery, or universal impossibility for competing systems.

## Findings that should change the experiment

1. **P1 — Replace the rhetorical baseline with a working competitor.** `README.md:17-23` and `demo.sh:131` describe the status quo as prose-only instructions, an unconstrained shell, unbound approval, and blind retries. There is no LangGraph or strong typed-Python implementation in the supplied tree. Those descriptions are not representative of what established libraries permit; see the primary sources below. Give the skeptic the same tools, observations, models, policies, and development budget and permit a competitive implementation.

2. **P1 — Separate recorded-provider rehearsal from agent evaluation.** `demo.sh:17` defaults to `fake`; `bin/claude:21-34` extracts the run number, loads a recorded answer from `rehearsal/replay/<run>`, and rewrites its paths. That tests orchestration against known answers; it cannot test diagnosis or generalization. `tests/smoke.sh:11-39` checks the expected presentation strings. Replays are openly labelled, so this is not hidden fabrication, but they must not count as agent benchmark results. Use fresh isolated runs and unseen scenario identities.

3. **P1 — Implement a stateful simulator before claiming recovery.** `scripts/daq_logs.py:29-46` copies fixed snapshots. `scripts/daq_recover.py:47-51` only appends text and sleeps; it neither changes simulated hardware nor checks a readback. Therefore the demo cannot measure recovered event flow, damage, partial recovery, or an action that fails after acceptance. A concrete misleading branch exists at `scripts/daq_recover.py:53`: omitting `--dry-run` returns `RECOVERED` although the body still only logs. The supplied workflow does pass `--dry-run` (`workflows/daq_diagnosis.py:154`), so this branch is not exercised by its normal path. Delete that branch or require independently observed postconditions.

4. **P1 — Test stale machine state, not only edited approval attachments.** `workflows/daq_diagnosis.py:124-131` freezes the displayed request and evidence, with a 30-minute approval timeout. The next effect at `:152-154` has no fresh acquisition or revalidation step. Preconditions in `scripts/playbooks.py:99-146` read static files without checking acquisition time, run/config epoch, or source coherence. Hardware can change while identical attachments remain on disk. Bind approval to a generation and action plan; reacquire relevant readbacks before acting; reject changed epochs and expired observations. Also test edits to sibling `xpm.txt` and `tmo.cnf`: the checker/actuator read those files (`scripts/check_playbook.py:33,49`; `scripts/playbooks.py:177,189-192`) even though only request/evidence are displayed. Whether the upstream runtime independently covers those undeclared reads needs verification; the bundle itself does not establish it.

5. **P1 — Narrow the confinement claim to the actual enforcement layer.** `confine/claude:48-56` configures Claude tool permission rules, including a general `Read` allow with enumerated hidden paths, and wildcard evidence/result edit paths. It does not create an OS sandbox or isolate the evaluator's hidden data. `confine/claude:17-20` and `README.md:66-67` overstate this as exactly two writable files and no operator configuration. In particular, `--setting-sources project` still selects project configuration; it is not a clean-room claim. A recorded refused Bash call proves that call was refused, not complete confinement. Keep the useful permission restrictions, inventory the effective configuration/tools, and use a separate evaluator boundary for private seeds and scoring. Claude's own documentation distinguishes tool permissions from OS sandboxing.

6. **P2 — Show a preflight defect that actually crosses the proposed type boundary.** `workflows/daq_diagnosis.py:23` explicitly identifies the contracts as runtime checks. `:137-139` acquires logs and calls the provider before there can be validation of its returned JSON. A compiler can reject known composition/type errors before spending money; it cannot predict arbitrary future provider bytes or hardware observations. Neither `tests/smoke.sh` nor `tests/test_evidence.py` compares compile-time rejection of an invalid composition against strict mypy/Pyright plus boundary validation. Measure separately: static wiring errors, malformed dynamic results, and physical invariants. Credit only checks the chosen implementation actually performs, including user-written validators.

7. **P2 — Treat the four playbooks as domain policy, not an orchestration invention.** `workflows/daq_diagnosis.py:29-33` and `workflows/prompts/diagnose.md:7-18` enumerate the accepted diagnoses. `scripts/playbooks.py:150-171` determines every recovery; model `fix` prose is never executed. That is sensible, but identical allowlisted policy can be shared by both systems. The evidence predicate (`scripts/evidence.py:20-22`) accepts sufficiently long substrings from any bundle line; it establishes textual presence, not causal support, source freshness, or relevance to the selected target. `rehearsal/TRIALS.md:44-47` acknowledges an unsupported story can pass. Score diagnosis/evidence quality separately from safe routing.

8. **P2 — Add missing/ambiguous telemetry and competing causes.** `scripts/playbooks.py:18` hardcodes one XPM, and predicates hardcode readout group zero. `:115-124` treats an empty parsed link table as no down links if other values are present; `:139-146` calls any `in_hw >= count` stuck, including a zero/zero sample. `:48-54` resolves an ambiguous host to the first active match. Such behavior matters with missing monitoring, multiple processes per host, inconsistent snapshots, and schema changes. Require explicit unknown/ambiguous states, repeated samples where justified, and fixtures with bad or absent observations. Validate the simulator's causal rules with a DAQ expert rather than declaring its labels to be physical truth.

9. **P2 — Keep a held-out evaluation after tuning the fixtures and checks.** `rehearsal/TRIALS.md:14-20` reports multiple fixture/wrapper revisions; `:49-59` changes quote validation after observing outputs; `:7-8` has a stronger model judge weaker models. Those are legitimate development activities, but the same two cases cannot provide independent validation. The two recorded Opus answers must remain training/rehearsal data. Freeze scenario families and score definitions before final evaluation, hold out fault combinations and random identities, and report all trials, false escalations, and uncertainty. Model agreement is not a DAQ relevance review.

## Strong existing alternatives, from primary documentation

| Requirement | Established mechanism and fair comparison |
|---|---|
| Early type-error detection | Python can use strict mypy/Pyright before execution. Pydantic documents typed constructor generation and stricter plugin configuration. Pydantic strict runtime validation addresses untrusted data, with documented differences for JSON. Compare compiler diagnostics and annotation burden, not “Python has no checks.” [Pydantic mypy](https://pydantic.dev/docs/validation/latest/integrations/dev-tools/mypy/), [strict mode](https://pydantic.dev/docs/validation/latest/concepts/strict_mode/). |
| Typed graph state and conditional control | LangGraph supports TypedDict/dataclass/Pydantic state and ordinary functions as nodes/conditional edges. Its typed state is not automatically a proof of every output or physical invariant. Give the baseline explicit boundary validators. [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api). |
| Human approval and recovery | LangGraph supports durable interrupts and checkpointers. Completed tasks can be restored, but interrupted nodes can rerun; the documentation explicitly discusses idempotency and task/interrupt order. A fair baseline uses a persistent checkpointer, isolated side effects, and an intent/idempotency/reconciliation policy. This is not a claim of automatic exactly-once hardware effects. [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts), [persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [graph re-execution](https://docs.langchain.com/oss/python/langgraph/graph-api#re-execution-and-idempotency). |
| File freshness and dependencies | Snakemake already builds file dependency DAGs and reruns on changes to input, modification time, code, parameters, and software environment. Existence/prefix conditions are expressible in ordinary guard code too. Compare integration and audit burden for semantic provenance, not bare expressibility. [Snakemake CLI](https://snakemake.readthedocs.io/en/stable/executing/cli.html#all-options). |
| Controls-specific waiting and interruption | Bluesky supports pause/abort/resume, suspenders driven by monitored signals, and checkpoints/cleared checkpoints for unsafe replay. Ophyd has completion status objects, timeouts, and subscriptions. These are credible controls components; do not equate an in-process pause with durability across SIGKILL. [Bluesky interruptions](https://blueskyproject.io/bluesky/main/state-machine.html), [ophyd status/core](https://blueskyproject.io/ophyd/user/reference/core.html), [ophyd-async devices](https://blueskyproject.io/ophyd-async/main/tutorials/using-devices.html). |
| Provider permissions | Claude already exposes tool-level permissions, separately from shell sandboxing. Therefore wrapper restrictions cannot be credited exclusively to Orc. [Permissions](https://code.claude.com/docs/en/permissions), [sandboxing](https://code.claude.com/docs/en/sandboxing). |

## Convergence criteria for the builder and skeptic

- Begin with a **bounded, falsifiable claim**: a defined invariant and failure family, named baseline versions, permitted integration code, equal model/tool budgets, and a measurable benefit. Examples include fewer duplicated policy checks, earlier rejection with zero expensive effects, or fewer unsafe retries for an equivalent operator workflow.
- Require a **steelman baseline**: plain typed Python plus strict boundary validation, and LangGraph where durable agent control is the relevant comparison. Permit Snakemake, Bluesky/ophyd, or an adapter when they are a natural fit. Record all adapter and simulator code on both sides; share domain recovery policy.
- Use a **stateful fault injector and separate evaluator**: scenarios alter observable state; actions have conditional/delayed/partial effects; evidence has run/config epochs; costs and side-effect attempts are logged independently. Include stale dependencies, schema drift, missing/prefixed artifacts, ambiguous telemetry, interrupted non-idempotent effects, recovered-before-approval, and unknown/compound faults. Domain reviewers must distinguish realistic DAQ incidents from orchestration-only stress tests.
- Builder submits artifacts, executable checks, causal claims, and cost accounting. Skeptic submits a concrete counterimplementation or reproducible counterexample with an audience-relevance objection. A neutral deterministic gate checks evidence completeness and invariants; it must not turn either agent's persuasive prose into the verdict.
- Freeze a candidate before hidden evaluation. Do not give either agent evaluator internals, answers, or hidden seeds; do give both the same public interface and development cases. Use paired trials; count unsafe actions, successful recovery with readback, false success, unnecessary escalation, expensive work before rejection, wall time, and implementation/maintenance burden.
- Accept **supported bounded advantage**, **baseline parity/dominance**, or **inconclusive/budget exhausted**. Include the counterexample and reproducible command for every rejected claim. Require both agents to address each other's strongest unresolved objection; consensus alone is insufficient.
- “Proof of impossibility” must be narrowly scoped (for example, impossibility of exactly-once external effects without a transactional/idempotent actuator under the stated crash model). A finite empirical search cannot prove no compelling Orc demo could ever exist. Universal expressibility claims are especially weak because both sides can call general-purpose Python; practical integration cost may still be a meaningful, testable advantage.
